# Rats and Ravens (PicoCalc Platformer)

Game title (per Thomas, 2026-09-25): **Rats and Ravens** — `GAME_TITLE`
in `platformer_config.h`, shown on the splash screen and as the desktop
window title. Build outputs keep their `picocalc-platformer-*` names.

An original 2D platformer for the ClockworkPi PicoCalc, built on the
Raspberry Pi Pico SDK, with a matching Windows/Linux SDL2 desktop port.
Author: Thomas Dzubin. Not based on or inspired by any specific existing
game.

**Current stage: milestone 4 — movement/jump/collision/camera-scroll/
scoring/randomly-generated-level tech demo, plus a full desktop port.**
Every level is randomly generated by `generate_level()` — gaps,
towers, platforms, foggy zones, pickups, and rat_ravens (a patrol hazard)
are all placed by `gen_*()` functions with retry-based placement, not an
exhaustive solvability proof. No real level THEME or art yet — geometry is
random, content is not. Don't add those without asking — confirm the next
milestone with Thomas first (see his "interview before new project/stage"
preference).

Released (per Thomas, 2026-09-26) — `CHANGELOG.md` was cleared out at
release, so it now holds only an empty `[Unreleased]` section; every
change from here on goes there as a bullet, and it (not this file) is the
authoritative user-facing history after release. Pre-release history was

## Hard invariants — do not violate without asking Thomas first

- **Power-ups are always optional.** The character must be able to
  progress through the whole game with zero power-ups — a power-up only
  ever makes something easier, never required. Any obstacle a power-up
  helps with must also be clearable without it. See
  [[platformer-powerups-optional]].
- **Every tower must be clearable by a well-timed double jump alone, with
  no power-up.** A tower is a full-width solid wall (no walking around,
  only over), so unlike most obstacles this is a hard safety cap, not a
  difficulty knob: `TOWER_H_MAX` (120) and `AIR_JUMP_VELOCITY` (double
  jump combo reach ~141px, an 11px margin) are load-bearing together — if
  you ever change one, re-verify the other still clears it (see "Jump
  physics" below for how to check this precisely).
- **No "hold key to jump higher" mechanic, ever.** Explicitly rejected by
  Thomas for both the base jump and the jewel ("not meant to be a
  'reduced gravity', but some kind of energy boost"). Jump height is set
  purely by which of three fixed launch velocities fires
  (`JUMP_VELOCITY`/`AIR_JUMP_VELOCITY`/`POWERUP_JUMP_VELOCITY`).
- **Never write "rat_raven" as "spider" in code, comments, or docs** — see
  [[picocalc-no-spiders-naming]]. Thomas may say "spider" or "ghost" in
  conversation meaning the same hazard; that's fine in chat, never in the
  repo.
- **Never use the term "HUD" anywhere** (code, comments, docs) — use
  "status line" instead. This is a cross-project rule; see
  [[picocalc-no-hud-naming]]. The tuning-only position/velocity readout is
  deliberately named separately (`ENABLE_DEBUG_READOUT`/
  `draw_debug_readout()`), not "status," to stay unambiguous from the
  level/time/score status lines.
- **Never define one obstacle/zone's position or size from another's.**
  Rely on the generic `SOLIDS[]` collision and reachability checks for any
  interaction between them instead — see
  [[picocalc-no-obstacle-position-coupling]]. (History: an early foggy-zone
  fix once derived `FOGGY_X` from `PLATFORM_X + PLATFORM_W` and had to be
  undone — the generic collision loop already handles this correctly for
  any layout.)
- **Never write `FOO_*/BAR_*` (or any comment that could close early) in a
  C block comment** — the literal `*/` closes the comment right there,
  causing misleading cascading errors far from the real bug. See
  [[c-comment-wildcard-slash-gotcha]]. The mirror-image mistake is just as
  real: an **unclosed** `/*` swallows everything up to the next `*/` it
  finds, including an entire `#define` line if one happens to have its own
  trailing inline comment — this actually happened (2026-09-24, from a
  manual hand-edit) and broke the build silently until compiled. Always
  verify comment balance in both directions before reporting a change
  build-ready (see "Verification habit" below).
- **Always ask before compiling or flashing, every single round**, no
  matter how recently a previous round was approved or how trivial the
  change looks. This has been violated more than once in this project's
  history and Thomas has had to correct it each time — see
  [[ask-before-recompiling]] and [[always-ask-before-flashing]]. The
  standing exception: a discrete-tick physics simulation run via a
  standalone `awk`/Python script (used to numerically tune jump constants
  before guessing) is NOT "building the project" and needs no go-ahead.

## Files

- `GAME_DESCRIPTION.md` — the long design overview that used to be
  `platformer.c`'s header comment (moved out 2026-09-26, per Thomas). Keep
  that header short; put overview-level text here instead.
- `platformer_functions.h` — every static function prototype for
  `platformer.c`, included right before `main()`. Add a prototype here (not
  inline in the .c) when a new static function is used before its
  definition. `rat_raven_t` is forward-typedef'd there (`struct rat_raven`).
- `platformer_variables.c` — every file-scope type (`solid_t`, `pickup_t`,
  `struct rat_raven`, `level_rules_t`) and variable (level arrays, player/
  score/sound/rendering state) of `platformer.c`. It is `#include`d by
  `platformer.c` before `main()` and is NOT compiled on its own (don't add it
  to a CMake source list). New globals go there, not in `platformer.c`, so the
  main file stays logic only (Thomas, 2026-09-26).
- `platformer.c` — the whole program. Raw south-bridge FIFO keyboard model
  (never calls `picocalc_init()`). Fixed-point (subpixel, no float),
  fixed-timestep physics in `step_physics()`. Everything is positioned in
  WORLD coordinates; only `fill_world()` translates through `camera_x` at
  the point of drawing.
  - **Collision:** `SOLIDS[]` is a fully-solid, axis-separated obstacle
    list (ground, towers, platforms) — the character can't pass through
    any side of one. `FOGGY_ZONES[]` are NOT solid: they only slow
    movement while overlapped (gravity off inside one; UP/DOWN each queue
    a bounded `FOGGY_STEP_PX` step worked off at `FOGGY_CLIMB_SPEED`,
    not a continuous latch — see `foggy_move_remaining`). Each zone's top
    edge is also a generic one-way landing ledge (a second loop right
    after the `SOLIDS[]` one), so climbing clear of a zone leaves the
    character standing on it, grounded, jumps refilled; `on_foggy_ledge`
    + `down_buffer_ticks` let a DOWN press step back down from exactly
    that ledge (including with the power-up active, which otherwise
    bypasses foggy-zone handling entirely).
  - **Jump physics:** three fixed launch velocities, no held-key
    variants — `JUMP_VELOCITY` (ground), `AIR_JUMP_VELOCITY` (double jump,
    `MAX_AIR_JUMPS`=1 extra), `POWERUP_JUMP_VELOCITY` (jewel — a
    real energy-boost launch, not reduced gravity). To re-tune any of
    these, simulate first: a small `awk`/Python script modeling
    `step_physics()`'s real per-tick order (`vy += GRAVITY_ACCEL; y +=
    vy`, same tick, semi-implicit Euler) gives the exact peak-height/combo
    reach for a candidate value — this project has been burned before by
    guessing "a bit higher" and getting it numerically wrong (the double
    jump was once genuinely, not just perceptually, under the platform
    band's max reach).
  - **Pickups:** `PICKUPS[]` is one generic `{x, y, type, taken}` list —
    `PICK_JEWEL` (sets `powerup_boost_active`/`powerup_ticks_remaining` —
    tick-based like the level timer, so a pause pauses it) and
    `PICK_COIN` (`+COIN_VALUE` score; other score sources are `STOMP_VALUE` per stomped rat_raven and the win screen's time bonus). One
    collection mechanism for both (plain overlap test), regardless of
    whether the pickup sits in open air, on a solid, or inside a foggy
    zone. Only a jewel pickup cures sickness instantly (gold coin does
    not) — plus a 30-second tick-based auto-cure (`SICK_CURE_TICKS`).
  - **Rat_ravens** (`RAT_RAVENS[]`, `rat_raven_t`) — a patrol hazard, same
    block size as the player (`RAT_RAVEN_SIZE` aliased to `PLAYER_W`, so
    they can't drift apart), white-outlined for visibility against the
    black background. Two kinds (`.flying`): **ground** ones patrol at
    `RAT_RAVEN_SPEED`, reverse off a tower, either end of the level or the edge of
    a gap (they never cross one); **flying** ones patrol a
    random fixed height (`FLYING_RAT_RAVEN_Y_MIN`/`_MAX`) at double speed,
    reverse off a tower OR a platform, and ignore ground/gaps entirely.
    Either kind's speed halves while inside a foggy zone
    (`rat_raven_in_foggy()`) — note this requires the `repositioned` bool
    pattern in the movement code (only snap `x_sub` to a whole pixel when
    a check actually picked one on purpose) so a halved, non-multiple-of-16
    subpixel speed still accumulates correctly instead of truncating to a
    permanent standstill (a real bug that shipped once). A touch has three
    mutually-exclusive outcomes, gated by `RAT_RAVEN_HIT_INVULN_TICKS` so
    continuous contact can't double-count: `powerup_boost_active` → shield
    (ends the power-up); already `sick` → death; otherwise → `sick = true`.
    ALL THREE remove the rat_raven (`bb->alive = false`). Landing on top from
    above (falling or off a ledge) stomps and kills it instead, leaving the
    player untouched — checked separately in the vertical resolve.
    `gen_rat_ravens()` keeps spawns `RAT_RAVEN_MIN_SPAWN_DIST` clear of the
    player's start, and guarantees at least one flying rat_raven per level
    regardless of how the per-spawn `FLYING_RAT_RAVEN_CHANCE_PCT` (25%) roll
    lands.
  - **Status lines** (`draw_status_lines()`, row 0-2 — NEVER call this a
    "HUD," see invariants above): `LEVEL:`+`TIME:` on one line, `SCORE:`
    on the next (both `STATUS_SCALE`, bigger text), and `LEVEL HIGH
    SCORE:` on a third, at normal (scale 1) text size, plus a message line.
    Each line only redraws when its own text changes, OR when something
    painted over it: `redraw_region()` records any repaint above
    `PLAYFIELD_TOP_Y` in `status_dirty_y0`/`_y1` (a full-screen repaint, or
    the player's erase at the top of a very high PicoCalc jewel jump), and
    `status_force_redraw` forces all of them. `level_high_score` (a static `int32_t`) is
    reset to 0 only in `generate_level()`, so it survives both a
    death-retry (`start_run()`) and the win-screen same-level retry below
    — it is scoped to the current level layout, not to `reset_player()`'s
    per-attempt state.
  - **Death/win:** `death_reason` (a `const char *`, set alongside
    `player_died = true` at its three set sites — timer expiry, falling
    past `FALL_RESPAWN_Y`, a rat_raven hit while already sick — reset to
    NULL in `reset_player()`) drives `show_death_screen()`'s "why" line;
    no score or time is shown on death. `show_win_screen()` (now
    returning `bool`) shows the elapsed time as `<N>s`, pauses ~1s, then
    runs a per-tick countdown that decrements both the displayed seconds
    AND the real `score` (score floors at 0 and simply stops decrementing
    there; the seconds display keeps counting to 0 regardless), beeping
    every `SCORE_COUNTDOWN_BEEP_EVERY` ticks — this is a REAL deduction,
    not cosmetic, since it settles what `score` is at the exact moment it
    gets compared against `level_high_score`, right after. **Must call
    `sfx_silence()` at its very top** (a real bug once let a
    pickup/rat_raven tone keep sounding through the whole win sequence,
    since this function never otherwise touches the sfx state machine).
    The same applies anywhere physics stops ticking for a while: pause,
    `confirm_quit()` and `choose_level()` all call `sfx_silence()` too.
    After the countdown settles, `level_high_score` is updated
    if beaten, then the function shows its own two-line prompt ("PRESS
    ANY KEY TO CONTINUE" / "PRESS ENTER TO RETRY LEVEL") and its own
    keyboard-drain pause (`pause_draining_keys()`), ending with
    `wait_any_key()` (which returns the key, so ENTER/RETURN can be told
    apart) rather than the shared `end_screen_pause_and_wait()` — the
    two screens diverge here, same reasoning as the earlier death/win
    drawing split. `run_demo()` calls `start_run()` (same level, high
    score kept) if that returns true, `win_level()` (new level, high
    score reset in `generate_level()`) otherwise — either way
    `reset_player()` zeroes `score` for the new attempt; **score never
    carries between levels or retries**, only `level_high_score` does.
    `end_screen_pause_and_wait()` is now death-only.
  - **Level generation:** `generate_level()` runs, in order: `gen_gaps()`
    (scratch list) → `gen_ground()` → `gen_towers()`/`gen_platforms()`
    (reject any candidate overlapping an existing solid — the collision
    resolver isn't a proper sweep/CCD solver, so solid-vs-solid overlap
    risks jitter/tunneling; a platform's test box is also padded by
    `PLAYER_H` above and below, so every platform keeps a player-height of
    clear space under it and can never turn a tower top into an
    unreachable crawlspace or merge with a tower into a taller wall) →
    `gen_rat_ravens()` (rejects a spawn overlapping any solid) →
    `gen_foggy_zones()`/`gen_fog()` (only reject overlap against other
    foggy zones — purely a visual concern, since a zone partly blocked by
    a solid is a valid, intentional obstacle) → `gen_pickups()` (rejects
    overlap against other pickups, visual, AND against any solid, since a
    buried pickup can't be collected and costs a missed-coin penalty). A
    pickup placed inside a foggy zone records it (`pickup_t.fog`) and
    rides along as the zone drifts; `spawn_x` restores it on a retry. A **floating** foggy zone placed too
    high to reach by ground/double-jump alone (`FOGGY_FLOAT_MAX_GROUND_REACH`)
    additionally requires `platform_near_foggy_float()` to find a platform
    within reach first — reject and retry otherwise. `world_width` is a
    runtime variable, always `LEVEL_SCREENS` (10) screens wide. Density formulas use `screens = world_width /
    REF_SCREEN_W` (a fixed 320, NOT the actual `WIDTH`) — see "Desktop
    scaling" below for why. PRNG is a small xorshift32
    (`rand_u32()`/`rand_range()`), deliberately not the Pico SDK's hardware
    RNG, so the desktop build needs no extra shim stub. No exhaustive
    solvability proof — reasonable physics-derived constraints (jump-range
    gap widths, `LEVEL_SAFE_MARGIN` guaranteeing solid ground at both ends)
    plus retry-with-reject placement, giving up gracefully (fewer objects
    than the density target) rather than hard-failing.
  - **Sound:** `sfx_play_happy()`/`sfx_play_sad()`/`sfx_play_impact()`
    start a tone via the driver's non-blocking `audio_play_sound()`; a
    tiny tick-driven state machine, `sfx_update()` (called once per
    physics tick, AND pumped manually by `pause_draining_keys()`, the
    end screens' pause loop, since physics stops ticking once
    `player_died`/`player_won`), counts down and either switches to a
    second tone or calls `audio_stop()`. Deliberately never
    `audio_play_sound_blocking()` for these — it sleeps for its whole
    duration and would freeze physics.
  - **Rendering:** `render_frame()` is two passes — ERASE everything that
    moved (drifted fog, collected pickups, rat_ravens, the player: each
    repaints its OLD footprint via `redraw_region()`), then DRAW (status
    lines, every rat_raven, the player last). Never interleave erase and
    draw per object: one object's erase would bite into another already
    drawn that frame (rat_ravens crossing used to flicker exactly this
    way). Sprites are fully opaque, which is why erasing only the old
    footprint is enough. A camera move replaces the erase pass with a
    viewport repaint.
- `platformer_config.h` — every `#define`/tunable constant. See the
  in-file design comments above `TOWER_H_MIN`/`_MAX`, the "Scale" section,
  and the rat_raven block for the reasoning behind non-obvious values; don't
  retune any of `GRAVITY_ACCEL`/the three jump velocities/`TOWER_H_MAX`
  without re-simulating the tower-clearability invariant above.
  - **Desktop scaling.** `SCALE_X(v) = v*WIDTH/320` is used ONLY for
    horizontal layout: camera dead zone, gaps, platform/tower/foggy-zone
    widths and spacing, rat_raven spawn distance, player start X,
    `FOGGY_FLOAT_PLATFORM_MAX_DX`. `SCALE_Y(v) = v*HEIGHT/320` is used
    ONLY for `GROUND_TOP` — the single deliberate vertical exception, kept
    so the ground band's on-screen proportion matches the PicoCalc
    (`GROUND_HEIGHT = HEIGHT - GROUND_TOP` derives from it automatically).
    **Every other vertical quantity is UNSCALED** on both builds: gravity,
    all three jump velocities, `MOVE_SPEED`, `RAT_RAVEN_SPEED`/
    `FLYING_RAT_RAVEN_SPEED`, foggy-zone speeds, and every solid's HEIGHT
    (tower/platform/foggy). **Every height band is defined relative to
    `GROUND_TOP`** (`PLATFORM_Y_*`, `FOGGY_FLOAT_Y_*`,
    `FLYING_RAT_RAVEN_Y_*`, open-air pickups), never as an absolute
    screen Y — absolute values silently sat ~150px higher above the
    desktop's scaled ground than on the PicoCalc (fixed 2026-09-25). This was a
    deliberate reversion after real playtesting on the 640x480 desktop
    build showed scaled motion "too fast" for unscaled sprite sizes, and
    because scaling `TOWER_H_MAX` up while leaving jump velocity unscaled
    (or vice versa) would break the tower-clearability invariant above.
    Player/rat_raven/pickup sprite SIZES are never scaled either (Thomas's
    own explicit deferral — a future request, not done yet).
    `REF_SCREEN_W` (fixed 320, independent of the real `WIDTH`) is what
    density formulas divide by, so the wider desktop viewport shows
    proportionally MORE content rather than the same content thinned out
    over more raw pixels.
  - `PLATFORM_DESKTOP` (set in `desktop/CMakeLists.txt`) is the project's
    only purely-behavioral (not size/constant) platform branch so far:
    ESC/Q really exit the process (after `confirm_quit()`) on desktop,
    vs. leaving to the PicoCalc UF2 Loader on firmware (V1.01A). Both go
    through `exit_to_loader()`: on firmware it asks the loader for its menu
    via the watchdog scratch registers (`LOADER_*` in `platformer_config.h`,
    the same hand-over PicoCalc-SD-Drive uses; the loader has no official
    app exit call) and reboots, so RP2040 and RP2350 behave identically;
    on desktop it just calls `exit(0)`. `is_quit_key()` (Q or ESC) is used
    by the splash screen and the death screen; ESC in the game is immediate
    on firmware, Q in the game still asks `confirm_quit()` first.
- `pickup_sprites.h` — 8x8 coin and jewel pictures (`PICKUP_USE_SPRITES`).
- `player_sprite.h` — 16x24 player picture (`PLAYER_USE_SPRITE` switches it off).
- `rat_raven_sprites.h` — 16x16 rat/raven pictures for the rat_ravens;
  `RAT_RAVEN_USE_SPRITES` in `platformer_config.h` switches back to squares.
- `CMakeLists.txt`, `pico_sdk_import.cmake` — firmware build config; a
  POST_BUILD step copies the `.uf2` to the top level as
  `picocalc-platformer-RP2040.uf2` / `-RP2350.uf2`. Also builds
  `${STARTER}/drivers/audio.c` + its PIO header, linking
  `hardware_pio`/`hardware_clocks`.
- `desktop/` — SDL2 build for Windows and Linux; a shim (`shim_*.c`,
  `pico/*.h`, `hardware/*.h`) re-implements the picocalc-text-starter
  driver API so `platformer.c` compiles unchanged.
  - `desktop/lcd.h` is a shadow header: `#include_next "lcd.h"` (GCC/clang
    extension) pulls in the real, untouched, 320x320 vendored `lcd.h`,
    then `#undef`/`#define`s just `WIDTH 640`/`HEIGHT 480`. Works because
    `desktop/` is first in the desktop build's include path — invisible to
    the firmware build. **Gotcha:** adding this kind of shadow/intercepting
    header can leave stale `ninja`-tracked objects that an incremental
    build won't know to rebuild, since their dependency file still points
    at the unmodified real header — do one full clean rebuild
    (`rm -rf build-windows && cmake ... && ninja ...`) the first time such
    a header is added or changed; ordinary incremental builds are fine
    afterward.
  - `desktop/shim_audio.c` is a real SDL2 audio backend (not a stub):
    `SDL_AudioDeviceID`, phase-accumulator square-wave generation per
    stereo channel, `SDL_LockAudioDevice()`/`UnlockAudioDevice()` around
    the shared frequency/playing state so the audio callback thread never
    reads a torn value. `SDL_INIT_AUDIO` is included in `shim_core.c`'s
    `SDL_Init()` flags.
  - `desktop/shim_input.c` already maps the full US keyboard (every
    printable key, shifted symbols, F1-F10, arrows, modifiers) into the
    south-bridge FIFO event model.
  - Output: `picocalc-platformer-Windows.exe` (SDL2 static) /
    `picocalc-platformer-Linux` (SDL2 dynamic, `libSDL2-2.0.so.0` shipped
    beside it).
- `picocalc-text-starter-main/` — vendored `picocalc-text-starter` (LCD,
  south-bridge, audio drivers) by Blair Leduc. **Do not modify anything
  here.**
- `CHANGELOG.md` — add a bullet under `[Unreleased]` whenever behaviour
  changes (same pass as the code + README edits).

## Building

VS Code Pico extension (Compile / Run), or from a terminal with
`PICO_SDK_PATH` set:

    cmake -B build -G Ninja
    ninja -C build

Output: `build/picocalc-platformer-<chip>.uf2` (`<chip>` is `RP2350` or
`RP2040`). Flash by copying to the `RPI-RP2` BOOTSEL drive.

Windows (MSYS2 UCRT64 shell, SDL2 installed):

    cmake -S desktop -B build-windows -G Ninja
    ninja -C build-windows

Linux (needs `libsdl2-dev`) — same `desktop/` build, SDL2 linked
dynamically, `libSDL2-2.0.so.0` copied next to the executable
(`$ORIGIN` run-path):

    cmake -S desktop -B build-linux
    cmake --build build-linux

This machine can't build Linux itself (no WSL/Docker/cross-compiler) —
Thomas builds and tests that target on his own Linux machine.

**Every round needs its own fresh build/flash go-ahead — see the hard
invariant above.** Both PicoCalc and desktop targets are now built
regularly during iteration (the project's earlier "don't compile desktop
until nearing final" policy has been superseded by actual practice since
the desktop port began).

**Verification habit before calling any change build-ready:** a wildcard-
slash-comment grep (`grep -nE '\*/[A-Za-z_]|[A-Za-z_]\*/'`) plus a
brace/paren balance check (`awk` totals over the whole file), and when
either flags something, a cumulative-depth-scan `awk` one-liner to
pinpoint the exact line rather than assume:

    awk '{o=gsub(/\(/,"("); c=gsub(/\)/,")"); depth+=o-c; if(depth<0){print NR": "$0" -> depth="depth; depth=0}}' file

There is one recurring, confirmed-harmless false positive: a comment near
`rat_raven_bounce_off_range()` using `[begin, begin+n)` half-open-interval
notation. Anything else flagged is real — including, as of 2026-09-24, the
mirror-image case (an unclosed `/*` swallowing a later `#define`), which a
plain "does it look closed" read can miss if the line that closes it isn't
the one you're looking at.

**BOOTSEL flashing workflow:** detect the drive
(`Get-Volume | Where-Object { $_.DriveType -eq 'Removable' -or
$_.FileSystemLabel -like '*RPI*' }`), verify it's genuine
(`cat /d/INFO_UF2.TXT`, expect `Model: Raspberry Pi RP2350`), copy the
`.uf2` (`Copy-Item ... -Destination "D:\" -Force`), then re-run
`Get-Volume` and confirm the drive is gone.
